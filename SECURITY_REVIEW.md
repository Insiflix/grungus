# Repository security and feature review

Reviewed 2026-10-20. Security fixes were implemented; the feature suggestions below were not implemented.

## Scope and method

Reviewed the first-party renderer/domain/infrastructure code, Electron main/preload/permissions/capture code, scripts and fixtures, root configuration, package manifest/lockfile, packaging, and documentation. At the final inventory this covered 192 JavaScript/TypeScript files and 12,603 lines, plus HTML/CSS/configuration and documentation. Used repository-wide dangerous-API/secret-pattern searches, manual review of trust boundaries and asynchronous operations, npm dependency audits, regression tests, production asset builds, Electron browser checks, and an unpacked Windows build.

Dependency distributions were assessed through the package graph, advisories, and integration boundaries rather than a line-by-line audit of every third-party source file. No live homeserver, real account credentials, real desktop capture, or second participant was used. Tests use synthetic users/media and isolated fixtures. This review does not certify the absence of vulnerabilities.

## Security findings and fixes

Severity describes the potential application impact and required conditions; dependency severities are npm's advisory classifications. Several findings are hardening of a conditional attack path, rather than demonstrated remote exploitation.

| ID | Severity | Finding before the fix | Implemented repair and evidence |
| --- | --- | --- | --- |
| S01 | Critical/high/moderate advisory entries | The dependency audit reported **15 affected package entries: 2 critical, 3 high, 10 moderate**. The critical entries were `shell-quote` and its parent `concurrently`. Other chains included `brace-expansion`, `source-map-js`, `http-cache-semantics`, and packaging's `global-agent`/`roarr`/`sprintf-js`. These totals include parent-package propagation, not 15 independent exploits. No chat-to-shell exploitation path was demonstrated. | Updated the lockfile and compatible dependencies; overrode `@electron/get` to use `global-agent` 4.1.3 instead of its vulnerable older logging chain. Both full and production-only npm audits now report **zero advisories**. Packaging succeeded with the override. |
| S02 | High, conditional widget compromise | Element Call shared the application's origin. Despite call-scoped widget capabilities, its scripts could access the parent DOM and parent desktop session bridge if compromised. | Separate `grungus-app://call` and `grungus-app://client` production origins; separate loopback hostnames during development. Restricted frame navigation, permissions, and parent CSP. Electron checks prove that the call page cannot read either the parent DOM or desktop bridge. Relevant files: `MatrixCallPolicy.ts`, `CallPanel.tsx`, `electron/main.ts`, `electron/permissions.ts`, `index.html`. |
| S03 | Medium, boundary hardening | Sensitive session load/save/remove and external-browser IPC did not validate the sender. | `electron/ipcSecurity.ts` now requires the current application's WebContents, its main frame, trusted origin, and application pathname. Calls from other frames, other windows, or the call document are rejected. External launches require HTTPS and reject embedded credentials. Unit tests cover the rejection cases. |
| S04 | High, login CSRF/session substitution | Browser login accepted a matching custom-protocol URL without binding it to the initiating attempt. An unsolicited callback could inject a login token or disrupt authentication. | Cryptographically random state, exact callback route, one state value, ten-minute expiry, and attempt consumption before exchange. The callback subscription ignores unrelated attempts. Tests reject missing/mismatched/duplicated state, wrong routes, expired attempts, and replay. File: `MatrixAuthProvider.ts`. |
| S05 | High, credential transport | Direct or discovered remote HTTP homeservers could receive passwords/tokens without TLS; a login response could replace the session homeserver via `well_known`. | Shared URL validation requires HTTPS for remote servers, rejects URL credentials/query/fragment, and preserves explicit loopback HTTP for development. Applied to discovery, registration, password/SSO login, stored sessions, and SDK startup. Tokens stay pinned to the validated login endpoint. URL and authentication tests cover these boundaries. |
| S06 | High on affected Linux systems | Electron can report encryption available while Linux uses the weak `basic_text` fallback. The previous check could persist credentials under that fallback while describing them as OS encrypted. | Session persistence and restore refuse `basic_text`; the live session can continue with a persistence warning. Platform-policy unit tests cover the fallback and an actual encrypted backend. File: `electron/sessionSecurity.ts`. No native Linux run was performed. |
| S07 | Medium | Concurrent credential save/remove operations could race: a save completing after logout could recreate the saved session file. Concurrent saves also shared a temporary filename. | A serialized session-operation queue preserves IPC ordering across load/save/remove and recovers after an operation fails. Unit tests exercise a delayed save followed by removal and a failed write followed by another operation. Files: `electron/sessionSecurity.ts`, `electron/main.ts`. |
| S08 | Medium | Late pagination, room/DM operations, token refresh, identity work, settings writes, and queued actions could complete after an account ended. Concurrent SDK startup could also reuse another session's pending initialization. | Added session/client/generation checks before publishing results or continuing operations; serialize different-account starts; reject late crypto startup; invalidate old secret-storage callbacks and zero discarded recovery keys. Settings mutations cannot carry an old blocked-user/room update into the next account. Runtime state clears even when credential-file removal fails. Regression tests cover late history, startup, secret callbacks, recovery keys, and settings writes. |
| S09 | Medium, availability | Media responses were buffered without enforcing actual byte counts, and hierarchy discovery could follow an unbounded sequence of unique pagination tokens. | Streamed download limits of 10 MiB for avatars, 32 MiB for images, and 256 MiB for other attachments; download timeouts; bounded hierarchy discovery at 100 pages/10,000 summaries. Tests include dishonest content lengths, oversized streams, and endless pagination. Files: `BoundedResponse.ts`, `MatrixAvatarLoader.ts`, `MatrixAttachments.ts`, `MatrixSpaceHierarchy.ts`. |
| S10 | High potential impact, decoder-dependent | Received unsupported media was passed to FFmpeg 6.1.1 as a native desktop process with the user's filesystem privileges, including plaintext temporary files. This created a broad attack surface for malformed codecs; this review did not reproduce a particular native decoder exploit. | Removed the native decoder IPC and production process path. Conversion now uses local FFmpeg WebAssembly in a disposable browser worker and virtual filesystem, with no desktop IPC or host filesystem access. Limits: 256 MiB input/output, two conversions, 180-second termination, restricted protocols. Real playback checks pass for WebM, MP4, MPEG, MP3, WAV, and AIFF. `ffmpeg-static` is development-only for generating synthetic fixtures; archive inspection confirms it and obsolete `mediaTranscoder` files are absent from the packaged app. |
| S11 | Low/medium, privacy | Arbitrary remote avatar URLs and received external GIFs could make automatic third-party requests, exposing the reader's network address and read timing. | Avatars must use authenticated Matrix media on the connected homeserver; non-MXC resolver bypasses are rejected. Received GIFs outside the explicit provider-CDN allowlist require a click. Referrers are suppressed. Tests verify rejected external avatars and click-before-image rendering. Provider CDN requests still occur for inline provider GIFs. |
| S12 | Medium, conditional widget misuse | The call driver accepted `encrypted: false` for encryption-key to-device events. The widget transport's built-in strict mode compared against the host's own origin, unsuitable for an isolated widget, and did not independently bind incoming messages to the frame window. | Reject plaintext call-key to-device sends. A capture-phase message gate validates both the exact iframe window and widget origin before the transport receives matching widget messages; IDs remain validated by widget-api. Tests reject forged source/origin messages and plaintext keys. Cross-origin widget handshake and camera-control checks pass. Files: `MatrixCallDriver.ts`, `WidgetMessageGuard.ts`, `scripts/element-call-media.js`. |
| S13 | Medium, capture privacy | Normal SDK shutdown did not dispose classic calls, and logout waited for network completion before stopping them. A delayed device-settings operation or camera-permission response could continue after shutdown/settings closure. | Dispose classic calls at shutdown, stop local SDK/call state before network logout, guard pending call start/answer, reject ignored callers, and stop a preview stream arriving after unmount. Tests cover delayed call setup and late camera permission. Files: `MatrixJsSdkClient.ts`, `MatrixDirectCalls.ts`, `SettingsPanels.tsx`. |
| S14 | Low/medium, hardening | The separately loaded call document had no explicit CSP. The main page's policy did not protect that document. | Added a call-page policy restricting scripts to local assets and WebAssembly, with no objects/base URLs/form submissions. Extracted the two trusted vendor bootstrap snippets into local files to avoid allowing arbitrary inline scripts. The widget smoke test rejects CSP violations. File: `vite.config.ts`. |

The original dependency audit is retained in `docs/security/audit-before.json`. A fresh `npm audit` is the authoritative current result.

## Verification

- `npm run typecheck`: renderer and Electron checks pass.
- `npm test`: **375 tests across 52 files pass**, including the new security regressions.
- `npm run test:media`: all six synthetic audio/video samples play with controls; unsupported formats use the worker conversion path.
- `npm run test:spaces`: compact DM spacing, standalone group chats, server creation, public channel discovery/join, voice participants, voice text chat, and distinct channel/group-call views pass.
- `npm run test:call`: isolated widget handshake, room state, voice lobby, narrow layouts, synthetic camera constraints, explicit screen-picker consent, and joined/minimized layout pass. Parent DOM/bridge access is blocked.
- `npm run test:security`: production renderer/Electron build, real custom-protocol origin isolation, main-page IPC, call-page CSP, and local decoder worker/WASM loading pass.
- `npx electron-builder --dir`: Windows unpacked packaging passes. Archive inspection confirms the WASM decoder is included and `ffmpeg-static`, native `ffmpeg.exe`, and obsolete `mediaTranscoder` files are absent.
- `npm audit` and `npm audit --omit=dev`: **zero reported vulnerabilities**.

## Remaining limits and release considerations

- No live-server penetration test, multi-device key recovery test, two-person RTC interoperability test, or native macOS/Linux run was performed. Unit tests cover Linux persistence policy; Windows Electron fixtures exercise actual browser isolation and synthetic media.
- A clean npm audit covers published package advisories. It does not certify bundled Electron/Chromium, codec internals, vendored Element Call dependencies, or undisclosed issues. The WASM decoder still needs updates and can consume substantial memory/CPU; its isolation and limits reduce impact rather than eliminating all denial-of-service risk.
- OS credential encryption protects the session file. The SDK's persistent crypto IndexedDB and browser profile are separate local data stores; this change does not add profile-wide encryption or securely erase historical caches on logout. Local OS-profile compromise remains outside the browser isolation boundary.
- Provider GIFs contact their media CDN. Calling reveals metadata to the configured homeserver/RTC services, and ordinary peer-to-peer 1:1 calls can expose peer network addresses. No relay-only mode was added.
- A Vite `VITE_*` provider key is distributed to client code and cannot be treated as a secret server credential. No tracked session tokens/private keys were identified in the pattern scan; that is not a complete Git-history or provider-account audit.
- The Windows packaging check is unsigned because no signing certificate is configured. Existing installers are not automatically republished by this review. Source fixes require rebuilding/restarting Electron before they take effect.
- Build output still reports a large renderer chunk and a future Vite config-loader import-extension warning. They did not fail verification.

## Missing features worth adding — suggestions only

| Priority | Suggestion | Evidence / expected benefit |
| --- | --- | --- |
| High | Per-room drafts, including attachments/reply targets | The composer keeps its draft in component state and resets on room changes. Preserve unsent work when switching between DMs, channels, and voice text chat; choose an explicit local-data privacy policy. |
| High | Message search across a room/server, with sender/date/media filters | Current search finds conversations and members; it does not search message content. Encrypted history needs local search/indexing rather than sending plaintext to a server. |
| High | Retry/resend/cancel controls for failed sends | Failed local echoes are visible, but recovery actions are limited. Keep the original body/attachment and show actionable delivery errors. |
| High | Create a multi-person DM directly | The people dialog creates a one-person DM. Existing standalone group rooms have their own list/call interface, but a select-multiple-people creation flow is missing. |
| Medium | Server channel categories, ordering, and onboarding | Spaces discover channels and support creation; add editable category/order presentation and optional starter channels to make a newly created server easier to use. |
| Medium | Threads and a pinned-message browser | Reply/edit/delete/reaction and pin controls already exist. A thread timeline and a navigable collection of pinned messages would make long conversations easier to follow. |
| Medium | Persistent voice connection controls | Add push-to-talk, deafen, connection/reconnect diagnostics, and a compact voice dock with clear device state. Avoid duplicating controls already provided inside Element Call. |
| Medium | Incoming group-call notifications and configurable ringing | Standalone group chats have a calling interface; add consistent background incoming-call alerts and preferences, with multi-device behavior tested. |
| Medium | QR verification and native OAuth/PKCE | SAS and recovery-key flows exist. Add the alternative verification and login paths after live-homeserver interoperability testing. |
| Release | Automated dependency/security checks, SBOM/license inventory, signed releases and update verification | Add CI coverage for unit/browser/security checks, dependency update review, and authenticated distribution. These need release-policy/provider choices and were not implemented automatically. |
| Maintenance | Refresh the general feature documentation | Some README deferred-feature entries still describe features that now exist, including attachment UI, message actions, and room administration. Reconcile the feature list with the current app. |
